## 流程驗收

1. 建立活動、兩個組別及費用 → 開放報名 → 訪客一次報名兩組 → 顯示編號與不含個資的 QR → 重複手機拒絕。
2. 指派評審並接受 Email 對應邀請 → 分組報到 → 結束本組報到 → 評分 3 位舞者 → 鎖定 2 強 → 保存配對 → 公布。
3. 目前場次投票 → 主辦核對並確認勝方 → 再公布 → 觀眾看到冠軍 → 暫停後顯示等待。
4. 手機搜尋、無結果、清除篩選、收合導覽、未登入工作台及 API 401。
5. 兩個獨立瀏覽器工作階段登入同一評審。第一階段保留草稿；模擬 503 寫入失敗時不顯示成功、不清空輸入。第二階段寫入後，第一階段舊版本被拒絕；同步後顯示雲端分數，明確核對及填原因，才可沿用草稿成功寫入。
6. 資料庫另驗證完整 **8 → 4 → 2 → 冠軍**，7 場持久化對戰、後輪建立後拒絕更正前輪、冠軍後拒絕再建輪。
7. 權限測試包含未登入、不同活動擁有者、錯誤角色、未指派組別、未驗證信箱、撤銷授權及私有表格/RPC 直接存取。
8. 規則測試包含結束報到僅限當前組、繳費仍可修改、已有評分不得重開、漏評／不足人數／無評審／截止線同分阻擋、鎖定後不得改分、相同報名請求冪等、跨裝置版本衝突、報名限流。
9. 備份測試包含 SHA-256 毀損檢查、活動與擁有者限制、交易回滾、跨活動資料拒絕、原有授權與稽核保留、已鎖定不得還原。
10. 公開快照驗證不含手機、繳費、私人評語、登入 Email、評審 ID 或稽核資料；未重新公布前看不到後臺新結果，暫停後不回傳舊快照。

## 尚未執行與限制

- **實際 Supabase 專案、Auth、SMTP／驗證信／邀請信、遠端 migrations 與 Vercel 部署**：使用者尚未建立專案，均未進行；不得把本機模擬測試當成已上線。建立後依 README 設定四個環境變數、Auth redirect 與 SMTP，並在雲端開發環境加入該 Supabase 專案網域。
- **實體裝置與瀏覽器**：未測真實手機相機掃描、iOS Safari、Android Chrome、投影大螢幕與實體全螢幕。
- **負載與故障**：已測兩個工作階段與模擬失敗，未做正式多人壓力、跨區延遲或斷網恢復的長時間測試。PGlite 不是遠端多連線 PostgreSQL 的效能／隔離驗收替代品。
- **還原**：刻意限制同一活動、同一擁有者、未鎖定且組別 ID 集合相同，避免破壞目前組別授權。舊系統遷移尚無來源格式，未實作猜測式匯入。
- **同步**：使用 20 秒工作台／10 秒公開頁輪詢，沒有實作即時訂閱。草稿在本次瀏覽器記憶體保留，離開或登出前確認，不保證重新載入後恢復草稿。
- **雲端環境設定**：`install_script` 與 `start_skill` 草稿已儲存，包含實測安裝／啟動／驗證步驟。尚未發布或驗證全新任務還原；環境設定發布與 Vercel 網站部署是不同操作。
